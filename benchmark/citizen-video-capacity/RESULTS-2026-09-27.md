## Resource and query observations

- Cloud Run scaled to a measured maximum of 7 instances.
- Maximum one-minute aligned p99 CPU utilization: 16.97%.
- Maximum one-minute aligned p99 memory utilization: 26.99%.
- No Firestore/Cloud Run quota or throttling errors were observed.
- The harness measured full `/feed` response latency. Firestore query execution was not separately instrumented, so an independent database-only latency number is not claimed.
- The 500,000-record/50-user run showed a cold-scaling outlier (p95 6.157 s); subsequent 100/250-user warm runs were faster. The 1,000,000-record/250-user p95 was 6.421 s.

## Seeder incident

The first 1,000,000-target execution `citizen-video-feed-seeder-znn6j` failed because the benchmark seeder queued 500,000 writes in memory. Logs proved `FATAL ERROR: Ineffective mark-compacts near heap limit Allocation failed - JavaScript heap out of memory` followed by signal 11. The benchmark-only seeder was changed to flush every 5,000 writes and use idempotent `set` operations. Replacement execution `citizen-video-feed-seeder-5jgqh` completed successfully and the marker was verified at 1,000,000.

## Capacity conclusions

- 1,000 simultaneous upload sessions: **NOT PROVEN**. Testing stopped at 500 because session p95 reached 11.838 seconds.
- 1,000,000 feed records: **PROVEN for the tested query**, through 250 concurrent synthetic feed users with 0% errors and p95 6.421 seconds.
- 1,000,000 uploads/week: **architecturally supported, not proven end-to-end**. This benchmark tested synthetic metadata/feed scale, not one million real uploads, Stream imports, or FFmpeg jobs.
- First demonstrated bottleneck: upload-session control-plane latency at 500 concurrent requests, not the cursor-paginated feed query.

## Verified physical Android new-video timing

Production video `8a1c3be6-51eb-4f2c-a46c-f032b8be284c` was traced through the authoritative Citizen Home feed path:

- Upload complete to `feedEligible=true`: 22.547 seconds.
- `feedEligible=true` to Android receiving the video: 1.767 seconds.
- Total upload complete to the new video reaching Android: approximately 24.3 seconds.
- Cloudflare processing: 11.916 seconds.
- Cloudflare READY to webhook received: approximately 10.13 seconds.

Conclusion: Android is not the material bottleneck. Once `feedEligible=true`, Android receives the new video in under two seconds. No optimization or code change is required from this result.
